01 · 开始之前

学习准备与建议顺序

MCP 是应用协议，不是模型训练方法。学习者需要理解 HTTP、进程标准输入输出、JSON、异步调用和基本权限控制。不了解 JSON-RPC 也可以继续，因为本文会说明其消息结构。

先备知识

  • 能够阅读 JSON，并区分对象、数组、字符串、数字与 null。
  • 知道客户端发送请求、服务端返回结果这一基本通信过程。
  • 能够使用 Python 3.11+ 或 Node.js 22.19+ 执行示例。
  • 理解环境变量不应写入公开代码库。

建议学习顺序

  1. 先确定 MCP 解决的问题以及不解决的问题。
  2. 再理解 host、client、server 和两层协议结构。
  3. 随后阅读 JSON-RPC、原语、能力声明和传输方式。
  4. 然后实现一个服务端，并使用 Inspector 检查消息与结果。
  5. 最后处理授权、安全、重试、可观测性和兼容性。
建议：先完成 stdio 示例，因为它不需要部署 HTTP 服务。理解消息语义之后，再研究远程服务与 OAuth 2.1。

02 · 基本概念

MCP 的精确定义、范围与限制

Model Context Protocol（MCP）是一项开放协议，用于规范 LLM 应用与外部数据源、工具及预定义提示之间的通信。它定义消息、能力、数据类型和传输要求，因此不同实现可以依照同一协议协作。

MCP 规定“如何描述与请求能力”，但是不规定模型如何推理，也不保证工具结果正确。host 仍需决定何时向模型提供信息、何时请求用户确认，以及如何处理服务端返回的数据。

MCP 的范围
属于 MCP不属于 MCP
工具、资源、提示及客户端能力的协议定义模型训练、微调和推理算法
JSON-RPC 请求、响应、通知与错误保证模型一定选择正确工具
stdio 与 Streamable HTTP 的传输约束业务数据库的一致性设计
HTTP 场景下的授权框架替代组织现有的身份与权限治理
能力声明与版本协商自动判定服务端代码可信

三个常见使用场景

  • 代码编辑器通过 MCP 服务查询项目文档、问题记录或构建状态。
  • 对话应用通过 MCP 工具查询库存，并在用户确认后创建订单。
  • 内部助手把只读知识库作为资源，把固定分析流程作为提示。

03 · 架构

Host、Client、Server 与信任边界

MCP 采用 host—client—server 架构。host 是面向用户的 LLM 应用；host 为每个服务端管理一个 client；每个 client 与一个特定 server 通信。一个 host 可以同时管理多个 client，但是各服务端应保持独立的权限和上下文范围。

核心角色与职责
角色主要职责不得默认信任的内容
Host管理用户界面、模型、权限确认、多个 client 与上下文选择服务端描述、工具结果、资源内容
Client处理协议版本、能力声明、请求关联、传输和结果解析未经验证的服务端消息
Server公开工具、资源和提示，并执行范围明确的业务逻辑客户端身份声明、模型生成的参数
Transport承载 JSON-RPC 消息不等同于身份认证或业务授权
Data layer定义 JSON-RPC 消息、原语、能力和生命周期语义不替代传输层安全

信任边界

每个 server 都是独立安全主体。host 不应把一个 server 的凭据、资源或完整对话自动提供给另一个 server。远程 server 与本地子进程也应采用相同的输入验证原则，因为本地代码同样可能包含缺陷或不可信依赖。

用户
  │ 明确授权与确认
  ▼
Host（模型、界面、策略、审计）
  ├── Client A ── stdio ───────── Server A（本地文件）
  └── Client B ── HTTPS/JSON-RPC ─ Server B（远程业务 API）

边界 1：用户 ↔ Host       边界 2：Host/Client ↔ Server
边界 3：Server ↔ 数据库   边界 4：Server ↔ 第三方 API

在 2026-07-28 修订版中，请求是自包含的。旧版的 initialize/notifications/initialized 握手与协议级会话已经移除。客户端可以先调用 server/discover 选择版本，也可以直接在每个请求的 _meta 中声明版本和能力。

04 · 协议消息

JSON-RPC、错误与能力协商

MCP 消息遵循 JSON-RPC 2.0。请求必须包含 jsonrpc、非空且当前唯一的 id、method，并可包含 params。响应以同一 id 关联请求，并且只包含 result 或 error 之一。

四类基础消息
类型必需成员是否有响应
请求jsonrpc、id、method是
成功响应jsonrpc、id、result不适用
错误响应jsonrpc、id、error.code、error.message不适用
通知jsonrpc、method否，而且不得包含 id

请求与成功响应

{
  "jsonrpc": "2.0",
  "id": 17,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "study-client",
        "version": "1.0.0"
      }
    }
  }
}

{
  "jsonrpc": "2.0",
  "id": 17,
  "result": {
    "tools": [],
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "study-server",
        "version": "1.0.0"
      }
    }
  }
}

错误与通知

{
  "jsonrpc": "2.0",
  "id": 18,
  "error": {
    "code": -32602,
    "message": "Invalid params",
    "data": { "field": "city" }
  }
}

{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}

通用错误应使用 JSON-RPC 标准代码：-32700 表示解析失败，-32600 表示无效请求，-32601 表示方法不存在，-32602 表示参数无效，-32603 表示内部错误。实现自定义错误时，只能使用规范允许的代码范围，并应避免在错误文本中暴露凭据或内部路径。

能力与版本

server/discover 用于查询服务端支持的协议版本、能力和身份。对于普通业务请求，客户端必须在 _meta.io.modelcontextprotocol/protocolVersion 中提供版本，并在 _meta.io.modelcontextprotocol/clientCapabilities 中提供客户端能力。服务端必须只使用客户端已经声明的能力。

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "server/discover",
  "params": {}
}

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersions": ["2026-07-28", "2025-11-25"],
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": {},
      "prompts": {}
    },
    "serverInfo": {
      "name": "study-server",
      "version": "1.0.0"
    }
  }
}

05 · 服务端能力

Tools、Resources、Resource Templates 与 Prompts

服务端原语对比
原语主要用途典型控制者示例
Tool计算、调用 API 或改变状态模型提出调用，host 可要求用户确认create_ticket
Resource读取由 URI 标识的内容应用或模型读取policy://travel
Resource template声明带参数的 URI 模板应用按参数解析 URIcustomer://{id}
Prompt生成可复用的消息模板用户明确选择review_incident

工具定义

工具至少具有名称、描述和输入 JSON Schema。输出可以包含文本、图像、音频、资源链接或嵌入资源；服务端还可以声明输出 Schema，并提供结构化结果。描述会进入模型上下文，因此必须简洁、准确，并明确副作用。

{
  "name": "convert_temperature",
  "title": "温度换算",
  "description": "把摄氏温度换算为华氏温度；不产生外部副作用。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "celsius": { "type": "number" }
    },
    "required": ["celsius"],
    "additionalProperties": false
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "fahrenheit": { "type": "number" }
    },
    "required": ["fahrenheit"]
  }
}

资源与资源模板

资源适合可寻址、以读取为主的内容。固定资源可使用确定 URI；同一类对象具有多个实例时，可以使用 URI 模板。资源内容仍是不可信输入，host 不应把其中的命令性文本视为系统指令。

{
  "uriTemplate": "customer://{customerId}/profile",
  "name": "customer-profile",
  "title": "客户资料",
  "description": "按客户标识读取资料；只读。",
  "mimeType": "application/json"
}

提示

提示是服务端提供的参数化消息模板。它适合由用户选择的固定工作流程，但是不适合执行业务副作用。客户端应在使用前显示提示名称、参数和生成内容。

{
  "description": "审阅一次事故记录",
  "messages": [
    {
      "role": "user",
      "content": {
        "type": "text",
        "text": "请按时间、影响、原因和改进项审阅事故 INC-42。"
      }
    }
  ]
}

06 · 客户端能力

Sampling、Elicitation、Roots 与用户同意

客户端能力允许 server 在处理原始请求期间要求额外输入。2026-07-28 使用 Multi Round-Trip Requests（MRTR）：server 返回 input_required，client 完成请求后，以新的 JSON-RPC id 重试原方法，并把结果放入 inputResponses。server 不再通过独立反向请求要求客户端处理这些能力。

客户端原语
能力作用用户控制要求版本状态
Sampling由客户端选择模型并生成内容允许检查提示、限制模型和审核结果2026-07-28 中保留但已弃用
Elicitation请求用户提供结构化字段或通过 URL 完成外部交互必须允许接受、拒绝或取消；不得索取敏感凭据当前客户端能力
Roots声明 server 可参考的文件系统根 URI用户决定公开哪些目录2026-07-28 中保留但已弃用

弃用不等于立即删除。新实现应避免把关键设计建立在已弃用能力上，同时需要理解这些能力，以便与旧客户端或过渡期实现兼容。

MRTR：请求用户输入

{
  "jsonrpc": "2.0",
  "id": 21,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm_create": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "是否创建工单？",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "confirmed": { "type": "boolean" }
            },
            "required": ["confirmed"]
          }
        }
      }
    },
    "requestState": "opaque-state-from-server"
  }
}

{
  "jsonrpc": "2.0",
  "id": 22,
  "method": "tools/call",
  "params": {
    "name": "create_ticket",
    "arguments": { "title": "数据库延迟" },
    "inputResponses": {
      "confirm_create": {
        "action": "accept",
        "content": { "confirmed": true }
      }
    },
    "requestState": "opaque-state-from-server",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": { "form": {} }
      }
    }
  }
}

requestState 应被视为不透明值。client 不应解析或修改它。server 必须再次验证原始参数、用户回复、权限和幂等键，因为第二次请求是新的请求。

07 · 传输

stdio 与 Streamable HTTP

传输层负责承载协议消息，但是不改变 JSON-RPC 方法语义。选择传输时，应根据进程位置、部署方式、身份要求和并发规模判断。

传输方式选择
项目stdioStreamable HTTP
进程关系client 启动本地 server 子进程server 是独立 HTTP 服务
消息承载stdin/stdout，每行一个完整 JSON-RPC 消息每个消息使用新的 HTTP POST
典型场景桌面应用、编辑器扩展、本地开发工具共享服务、集中部署、多用户系统
授权通常依赖本地进程与文件权限适用 MCP OAuth 2.1 授权框架
主要风险环境变量泄露、工作目录过宽、stdout 混入日志令牌泄露、来源校验不足、代理超时、跨租户访问

stdio 要求

  • server 从 stdin 读取 JSON-RPC，并向 stdout 写入协议消息。
  • 日志应写入 stderr。stdout 中的普通日志会破坏消息解析。
  • client 应显式设置命令、参数、工作目录和允许的环境变量。
  • 进程退出时，client 应区分正常关闭、启动失败和请求超时。

Streamable HTTP 要求

  • server 提供单一 MCP 端点，并接受 HTTP POST。
  • client 对每个 JSON-RPC 请求或通知分别发送新的 POST。
  • Accept 应同时声明 application/json 与 text/event-stream。
  • server 可返回单个 JSON 对象，也可为当前请求返回 SSE 流。
  • 长期变更通知通过 subscriptions/listen 的响应流传递，而不是依赖协议级会话。
POST /mcp HTTP/1.1
Host: mcp.example.com
Content-Type: application/json
Accept: application/json, text/event-stream
Authorization: Bearer <access-token>
MCP-Protocol-Version: 2026-07-28

08 · 原始协议

一组最小 JSON-RPC 交换

下面的四条消息展示版本查询、工具枚举与工具调用。为了便于阅读，消息采用缩进格式；stdio 实际传输通常把每条消息序列化为单行。

// 1. client → server：查询版本与能力
{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{}}

// 2. server → client：声明服务端能力
{"jsonrpc":"2.0","id":1,"result":{"protocolVersions":["2026-07-28"],"capabilities":{"tools":{}},"serverInfo":{"name":"unit-converter","version":"1.0.0"}}}

// 3. client → server：枚举工具
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{},"io.modelcontextprotocol/clientInfo":{"name":"raw-client","version":"1.0.0"}}}}

// 4. server → client：返回工具定义
{"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"convert_temperature","description":"Convert Celsius to Fahrenheit","inputSchema":{"type":"object","properties":{"celsius":{"type":"number"}},"required":["celsius"],"additionalProperties":false},"outputSchema":{"type":"object","properties":{"fahrenheit":{"type":"number"}},"required":["fahrenheit"]}}]}}

// 5. client → server：调用工具
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"convert_temperature","arguments":{"celsius":20},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}

// 6. server → client：返回文本与结构化结果
{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"20 °C = 68 °F"}],"structuredContent":{"fahrenheit":68},"isError":false}}

示例中的注释不是合法 JSON，因此复制到程序前应删除注释。协议实现还应限制消息大小、验证 Schema、处理取消和超时，并为请求标识记录关联日志。

09 · Python 实现

完整的 Python MCP 服务端

以下示例针对官方 Python SDK v2 的 MCPServer API，并使用 stdio。它提供一个工具、一个固定资源、一个资源模板和一个提示。安装命令为 python -m pip install "mcp[cli]>=2,<3"。

"""study_server.py — MCP 2026-07-28 教学服务端。"""

from __future__ import annotations

from mcp.server import MCPServer

mcp = MCPServer("study-python-server")

CUSTOMERS = {
    "c-100": {"id": "c-100", "name": "Lin", "tier": "standard"},
    "c-200": {"id": "c-200", "name": "Chen", "tier": "premium"},
}


@mcp.tool()
def convert_temperature(celsius: float) -> dict[str, float]:
    """把摄氏温度换算为华氏温度；不访问网络，也不修改外部状态。"""
    if not -273.15 <= celsius <= 1_000:
        raise ValueError("celsius must be between -273.15 and 1000")
    fahrenheit = round(celsius * 9 / 5 + 32, 2)
    return {"fahrenheit": fahrenheit}


@mcp.resource("policy://support")
def support_policy() -> str:
    """返回只读的客户支持政策。"""
    return "标准客户：2 个工作日内响应；高级客户：4 小时内响应。"


@mcp.resource("customer://{customer_id}/profile")
def customer_profile(customer_id: str) -> dict[str, str]:
    """按客户标识返回只读资料。"""
    if customer_id not in CUSTOMERS:
        raise ValueError("unknown customer_id")
    return CUSTOMERS[customer_id]


@mcp.prompt()
def review_ticket(ticket_id: str, severity: str = "medium") -> str:
    """生成工单审阅提示。"""
    allowed = {"low", "medium", "high"}
    if severity not in allowed:
        raise ValueError(f"severity must be one of {sorted(allowed)}")
    return (
        f"请审阅工单 {ticket_id}。严重程度：{severity}。"
        "请列出事实、待确认信息、风险和下一步建议，不要执行修改操作。"
    )


if __name__ == "__main__":
    # 默认使用 stdio。协议消息使用 stdout，普通日志应使用 stderr。
    mcp.run()

启动与检查

python -m venv .venv
. .venv/bin/activate
python -m pip install "mcp[cli]>=2,<3"
python study_server.py

直接执行时，进程会等待 client 从 stdin 提供协议消息，因此终端可能没有普通文本输出。这是预期行为。开发期间更适合使用 Inspector 启动并检查该文件。

查看仓库中的完整 Python 示例。该文件还包括 Pydantic 参数约束和业务错误转换。

实现说明

  • 类型标注用于生成输入或输出 Schema，但是业务范围仍需显式验证。
  • 工具文档字符串会影响模型选择，因此需要说明用途、副作用和约束。
  • 资源函数应保持只读语义；需要修改状态时应改用工具。
  • 示例使用内存数据。生产服务应增加认证、租户隔离、审计和超时。

10 · TypeScript 实现

完整的 TypeScript MCP 服务端

以下示例针对官方 TypeScript SDK v2。它使用 @modelcontextprotocol/server、stdio 子路径和 Zod v4，并提供一个具有结构化结果的工具。

// server.ts — MCP 2026-07-28 教学服务端
import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import * as z from "zod/v4";

const server = new McpServer({
  name: "study-typescript-server",
  version: "1.0.0",
});

server.registerTool(
  "convert_temperature",
  {
    title: "温度换算",
    description: "把摄氏温度换算为华氏温度；不产生外部副作用。",

    }),
    outputSchema: z.object({
      fahrenheit: z.number(),
    }),
  },

    return {
      content: [

      ],
      structuredContent: { fahrenheit },
    };
  },
);

11 · Host 逻辑

简化的 MCP 客户端决策周期

协议客户端只负责通信仍然不够。host 还需决定哪些工具可提供给模型、哪些调用需要用户确认，以及如何把结果返回模型。下面是一个有明确限制的伪代码示例。

async def answer_user(user_text: str) -> str:
    tools = await mcp_client.list_tools()
    allowed_tools = policy.filter_tools(
        tools,
        user=user,
        conversation=conversation,
    )

    for step in range(MAX_MODEL_STEPS):
        model_reply = await llm.generate(
            messages=conversation,
            tools=allowed_tools,
        )

        if model_reply.final_text is not None:
            return model_reply.final_text

        call = validate_single_tool_call(model_reply.tool_call, allowed_tools)

        if policy.requires_confirmation(call):
            approved = await ui.confirm(
                tool_name=call.name,
                arguments=redact_secrets(call.arguments),
                consequence=policy.describe_consequence(call),
            )
            if not approved:
                conversation.add_tool_result(call.id, "用户拒绝此操作")
                continue

        try:
            result = await with_timeout(
                mcp_client.call_tool(call.name, call.arguments),
                seconds=15,
            )
        except TimeoutError:
            result = {"isError": True, "message": "工具调用超时"}

        audit.write(
            user_id=user.id,
            tool=call.name,
            argument_digest=digest(call.arguments),
            outcome=summarize(result),
        )
        conversation.add_tool_result(call.id, sanitize_tool_result(result))

    return "已达到本次请求的工具调用次数限制。"
  1. 发现：查询能力和工具，并根据身份与任务过滤。
  2. 推理：向模型提供最少必要的工具定义。
  3. 验证：检查名称、参数 Schema、大小、租户和权限。
  4. 确认：对写操作、费用、外发数据或高风险操作请求用户同意。
  5. 执行：设置超时、取消和并发限制。
  6. 处理结果：把结果视为不可信数据，删除不应进入模型上下文的字段。
  7. 审计：记录主体、工具、参数摘要、授权依据、结果与耗时。

循环必须具有最大步数与总时间限制。模型请求重试并不代表业务操作可以安全重试，因此 client 必须依据工具的幂等语义决定是否重试。

13 · 身份与权限

HTTP 授权、OAuth 2.1 与最小权限

MCP 的授权规范适用于基于 HTTP 的传输。受保护的 MCP server 是 OAuth 2.1 资源服务器，MCP client 是 OAuth 2.1 客户端，授权服务器负责用户交互与令牌签发。stdio 通常不使用这一 HTTP 授权流程。

推荐流程

  1. client 请求受保护资源，server 在需要授权时返回 401 Unauthorized。
  2. WWW-Authenticate 指向 OAuth 受保护资源元数据，并可说明所需 scope。
  3. client 读取资源元数据和授权服务器元数据。
  4. client 使用授权码流程和 PKCE 请求用户授权。
  5. client 取得访问令牌后，再次请求 MCP 端点。
  6. server 验证签名、签发者、有效期、scope、资源 audience 与其他约束。
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource", scope="reports:read"
Content-Type: application/json

{
  "error": "insufficient_authorization"
}

必须实施的验证

  • 最小权限：只请求当前操作所需 scope，并允许增量授权。
  • Audience：server 必须拒绝签发给其他资源的访问令牌。
  • Issuer：client 必须验证授权响应中存在的 iss 与已记录签发者一致。
  • 重定向 URI：client 和授权服务器必须严格匹配已注册 URI。
  • PKCE：公共 client 不得依赖可提取的静态 client secret。
  • 令牌处理：令牌不得进入模型上下文、URL 查询参数、普通日志或工具结果。
禁止令牌转发：MCP server 不应把收到的访问令牌直接提供给下游 API。下游服务需要独立的 audience 与令牌交换或独立授权，否则会破坏令牌边界。

14 · 安全

提示注入、危险操作与审计

MCP 扩大了模型可读取的数据和可请求的操作，因此安全控制必须位于模型之外。资源内容、工具描述、提示模板、工具结果和错误文本都属于不可信输入。它们不能修改系统策略，也不能自行取得更高权限。

威胁与控制
威胁示例主要控制
提示注入资源文本要求模型泄露其他 server 的数据来源标记、上下文隔离、输出过滤、权限检查
恶意工具描述描述声称调用无需用户批准忽略描述中的策略声明，采用 host 本地策略
参数外泄模型把对话中的密钥作为工具参数参数预览、秘密检测、字段级允许列表
破坏性操作删除数据、发送消息、产生费用显式确认、分级权限、预览、幂等键、恢复机制
结果污染工具结果包含伪造的系统指令把结果标记为数据，限制可进入模型的字段
供应链风险本地 server 依赖被替换固定版本、校验来源、最小进程权限、依赖扫描

危险操作分级

  • 低风险：读取公开资料或执行无副作用计算，可以依据用户设置自动执行。
  • 中风险：读取私有数据或产生有限费用，应显示目标、字段与范围。
  • 高风险：删除、发布、付款、权限变更或批量修改，必须逐次确认并提供明确后果。

审计事件建议结构

  "trace_id": "tr_8f2c",
  "actor": { "type": "user", "id": "u_104" },
  "server": "ticket-service",
  "tool": "create_ticket",
  "argument_digest": "sha256:…",

    "scopes": ["tickets:write"],

审计日志应避免记录完整提示、凭据和敏感参数。需要调查时，可以依靠受控的关联标识定位受保护记录。日志的保存期限、访问权限与删除策略应符合组织要求。

16 · 选择

常见误区与原语选择指南

常见误区

“MCP 是模型插件市场。”
不准确。MCP 是通信协议；服务发现、分发、信誉和计费可以由其他系统实现。
“采用 MCP 后，模型会正确使用所有工具。”
不准确。MCP 规范化工具描述和调用，但是模型选择、权限策略与结果验证仍由 host 负责。
“所有能力都应定义为工具。”
不准确。只读且可寻址的数据通常更适合作为资源；用户主动选择的消息模板更适合作为提示。
“本地 stdio server 天然安全。”
不准确。本地进程可以读取继承的环境变量与文件权限，因此仍需最小权限和来源校验。
“HTTP 传输本身已经提供业务授权。”
不准确。TLS 保护传输，OAuth 提供授权框架，业务服务仍需检查租户、对象和操作权限。
“2026 版仍需要 initialize 握手和会话标识。”
不准确。修订版 2026-07-28 已移除协议级握手与会话，每个请求携带版本和客户端能力。

选择流程

Tool、Resource 与 Prompt 决策表
问题是否
是否可能产生副作用、费用或外部 API 调用？选择 Tool继续判断
结果是否由 URI 标识，并且主要用于读取？选择 Resource继续判断
同类资源是否需要 URI 参数？增加 Resource Template使用固定 Resource
内容是否是由用户主动选择的消息模板？选择 Prompt重新审查需求

一个业务功能可以同时使用多种原语。例如，客户资料可以作为资源，创建工单可以作为工具，事故复盘格式可以作为提示。各原语应具有单一且清楚的职责。

17 · 实践

从入门到高级的练习

练习 1：识别消息类型

级别：入门

为请求、成功响应、错误响应和通知各写一条 JSON-RPC 消息。检查请求标识是否唯一，并确认通知没有 id。

验收标准

四条消息都能通过 JSON 解析；响应标识与请求一致；错误包含整数代码和消息。

练习 2：设计原语

级别：入门

为“查询订单、取消订单、生成投诉分析模板”分别选择 Tool、Resource 或 Prompt，并说明用户控制方式。

参考方向

查询订单适合资源或只读工具；取消订单是高风险工具；分析模板适合提示。具体选择取决于寻址方式和产品交互。

练习 3：扩展 Python 服务

级别：中级

增加 create_ticket 工具。要求验证标题长度、使用幂等键，并以结构化结果返回工单标识和状态。

验收标准

重复使用同一幂等键时只创建一条记录；无效输入不产生写操作；工具描述明确说明副作用。

练习 4：Inspector 边界测试

级别：中级

测试缺失字段、额外字段、极大数字、空字符串、并发调用和取消。记录每项预期结果与实际结果。

验收标准

错误可区分且不含秘密；服务在失败后仍可处理新请求；取消不会留下不一致数据。

练习 5：实现 MRTR

级别：高级

让工具在缺少确认时返回 elicitation 输入请求。client 拒绝时不得执行；接受时使用新请求标识和原始 requestState 重试。

验收标准

三种用户结果均已处理：接受、拒绝、取消。server 不解析 client 提供的伪造状态，并重新检查权限。

练习 6：生产故障演练

级别：高级

模拟 OAuth scope 不足、下游 429、响应超时和重复 POST。为每种情况确定重试、用户提示、指标与审计字段。

验收标准

不会自动重试非幂等写操作；令牌不进入日志；错误指标可以按类型聚合；重复请求不会产生重复业务对象。

Audience
